# Code-path inventory of the kernels

Generated by `lean/paths_summary.py` from `lean/paths/<kernel>.json` (produced by `lean/analyze_paths.py` from
`kttool paths <kernel> <64 + 2*NODES> 400000 0`: the concrete model run from `initState` on the test message for
every count `0 .. 64 + 2*NODES`).  Model: the object code of branch `paths` (= `lean-verification` + PR #17).

* **classes**: counts whose executed instruction paths coincide up to the number of iterations of the outer
  loop (the loop head is the instruction whose visits cut the path of the largest count into the longest
  repeated piece: the batch call / batch body).
* **count readers**: forward taint from the count register (x86 `rdx`, AArch64 `x2`, RISC-V `a2`) through
  registers, flags and stack cells (named by abstract base + offset); `address` = a count-derived value used
  only as a memory base, `vl` = the RVV vector length.
* **batch**: x86 — the batch subroutine (`.call` target to its `.ret`); AArch64/RISC-V — the loop body.
* every count of every kernel gives the right digests for the nodes it hashes itself, never errs, and every
  tail call hands over `input + 64·done`, `output + 32·done` and the remaining count (`handover`).

## Findings for the multi-batch / tail composition proof

1. **No failures.** Every count `0 .. 64 + 2·NODES` of every kernel entry (28 entries: 24 kernels, RVV at
   VLEN 128/256/512) halts without `err`, writes the right digests for the nodes it hashes itself, and every
   tail call hands over `input + 64·done`, `output + 32·done` and `count − done` (checked for all 8 runtime
   threshold settings below as well).
2. **x86: the batch subroutine never reads the count data-wise.** In the avx2_x5/x6/x9/x10 and avx512_x9(d)
   batches `rdx` (and `rax`) are only spilled at the start and refilled at the end (`storeq`/`loadq` of the same
   stack slot); all other x86 batches do not touch it.  The count is read only by the frame: entry policy
   (`cmp rdx, 1` / `bt rax, rdx` masks), the loop test, the tail policy and the padded-tail copy loops (`mov rax,
   rdx` … `dec`).  ⇒ the loop body is count-independent given `rdx ≥ NODES`; per-count work is confined to small
   frame segments.
3. **AArch64 scalar/x3 kernels**: `x2` is spilled/filled around the batch and drives only the loop/tail branches
   (`subs`/`cmp` + `b.cond`, `cbz`).  **sha3_x2 / neon_x2** (2 nodes per batch): for an odd count the last batch
   selects the second node's input pointer with `cmp x2, #2; csel x3, x3, x1, cs; csel x4, …` (the node is
   duplicated and its digest not stored) — a count-dependent *pointer* choice inside the batch body
   (`address` readers), no count-dependent data.
4. **RVV**: `vsetvli` on `min(count, VLMAX)` makes `vl` count-dependent; every vector instruction of the batch
   reads it (tail lanes undisturbed).  No count value enters vector data.  Misaligned buffers take the bounce
   path (not exercised here: the harness buffers are aligned).
5. **Runtime-settable thresholds (a path the single-setting model does not show).** Two kernels read a `.data`
   word that the library sets at calibration time (any value through the public setters):
   avx2_x4 `.Lsmall_tail_max` (word 112 of the constant image; default 1, `keccaktree_detect` sets 1 or 2) and
   avx2_x10 `.Lmid_tail_max` (word 112; default 4, detect sets 5 or 9).  The model takes the `.data` image as
   constants, so the proofs must quantify over these words.  Explored with `KT_PATCH=112:v`
   (`avx2_x4_stmax{0,2,3}`, `avx2_x10_mtmax{5..9}`): new tail targets appear (avx2_x4 → avx2_x2 for 2..3 left),
   all correct.  Behaviour is determined by `min(value, NODES−1)` classes: avx2_x4 {0–1, 2, ≥3},
   avx2_x10 {≤4, 5, 6, 7, 8, ≥9}.
6. **Tail-call graph** (kernel → targets): x86_x1 ← everything x86; avx2_x2 → x86_x1; avx2_x4 → x86_x1, avx2_x2;
   avx2_x5 → avx2_x4, x86_x1; avx2_x6 → avx2_x4, avx2_x5, x86_x1; avx2_x8 → avx2_x4, avx2_x5, x86_x1; avx2_x9/x10 →
   avx2_x4, avx2_x5, avx2_x8, x86_x1; avx512vl_x4(d) → x86_x1; avx512_x8(d) → avx512vl_x4(d), x86_x1;
   avx512_x9(d) → avx512_x8(d), avx512vl_x4(d), x86_x1; sha3_x3, neon_x3 → scalar_x1; sha3_x3r → sha3_x2.
   The graph is acyclic (every target hashes fewer nodes per call or is the 1-node kernel), so a library theorem
   by induction over this order (then over count) is well-founded.  Entry tail calls hand over the *whole* count
   (`done = 0`, e.g. avx2_x9 → avx2_x8 for 8/12/16).
7. **Classes are small.** Up to the number of loop iterations, a kernel has 3 (1-node and RVV kernels) to 29
   (avx2_x10) path classes over `0 .. 64 + 2·NODES`; beyond 64 the classes repeat with period NODES (the
   `< 64` policy masks are the only count-range checks: `cmp rdx, 63; ja`).
